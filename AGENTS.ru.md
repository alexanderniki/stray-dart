# AGENTS.md — Руководство для AI-агентов по проекту `stray-dart`

Этот документ определяет операционный контракт, архитектурные инварианты и правила рабочего процесса, которым обязаны строго следовать любые AI-агенты при работе в этом репозитории.

---

## 1. Обзор проекта и архитектура

`stray` — легковесная, надежная консольная утилита на Dart для случайного выбора и вывода строки из текстового файла с поддержкой обрезки (`-t, --truncate`) и переноса строк (`-w, --wrap`).

- **SDK:** Dart 3.14+ (Sound Null Safety, строгий режим анализатора).
- **Архитектура:** Прагматичная гексагональная архитектура (Ports & Adapters):
  - `lib/src/core/`: базовые типы (`Result<S, F>`, `AppError`).
  - `lib/src/domain/`: чистая бизнес-логика (`StringPicker`, `StringFormatter`, порты `LineReader`, `RandomGenerator`). **Запрещено импортировать `dart:io` или сторонние библиотеки.**
  - `lib/src/infrastructure/`: адаптеры ввода-вывода (`FileLineReader`, `SystemRandomGenerator`).
  - `lib/src/cli/`: CLI-раннер, парсинг аргументов с `package:args`, форматирование, разделение потоков `stdout`/`stderr`, маппинг exit-кодов.
  - `bin/stray_dart.dart`: Composition Root. Ручная сборка графа зависимостей через Constructor Injection.

---

## 2. Ключевые архитектурные инварианты (обязательные для соблюдения)

1. **Конституция проекта:** ориентироваться на `docs/constitution.md` и `docs/constitution.ru.md` как на высший источник правил и стандартов.
2. **Чистый домен:** слой `domain/` должен оставаться 100% чистым Dart-кодом. Никаких зависимостей от платформы или `dart:io`.
3. **Result Pattern для ошибок:**
   - Не использовать `throw` для ожидаемых ошибок предметной области или ввода-вывода.
   - Все потенциально сбойные операции возвращают `Result<T, AppError>`.
   - Иерархия ошибок `AppError` типизирована и транслируется в понятные сообщения и exit-коды.
4. **Минимализм зависимостей:**
   - В runtime разрешены только минимально необходимые пакеты (`package:args`).
   - Запрещено добавлять тяжелые фреймворки (DI-контейнеры, библиотеки функционального программирования и т.д.).
   - Не добавлять зависимости в `pubspec.yaml` без явного согласия пользователя.

## 3. Рабочий процесс Spec-Driven Development (SDD) и TDD

Агенты обязаны выполнять разработку строго в следующем порядке:

```
[Спецификация] ──> [Согласование] ──> [Тесты (Red)] ──> [Реализация (Green)] ──> [Рефакторинг]
```

1. **Спецификация прежде всего (`spec/<feature>.spec.md`):**
   - Никакой код не пишется, пока спецификация фичи не создана и не одобрена пользователем.
   - Спецификация должна содержать контракты CLI, граничные случаи и BDD-сценарии (`Given-When-Then`).
2. **Строгий TDD (Фаза Red):**
   - Сначала пишутся модульные и интеграционные тесты в `test/`.
   - Запуск `dart test` обязан подтвердить, что новые тесты падают (КРАСНЫЙ СТАТУС), до написания кода реализации.
3. **Реализация (Фаза Green):**
   - Пишется минимально необходимый код для прохождения тестов.
4. **Рефакторинг и очистка:**
   - Функции должны оставаться чистыми, компактными и строго типизированными.
   - 100% тестов должны оставаться зелеными.

## 4. Контроль качества (Quality Gates)

Перед завершением любого шага агент обязан убедиться в прохождении трех проверок:

```bash
# 1. Форматирование кода (лимит строки 80 символов)
dart format --output=none --set-exit-if-changed .

# 2. Статический анализ (строгий режим: strict-casts, strict-inference, strict-raw-types)
dart analyze

# 3. Автоматизированные тесты (100% прохождение)
dart test
```

---

## 5. Стандартные команды CLI и разработки

- **Запуск в разработке:**
  ```bash
  dart run bin/stray_dart.dart [флаги] <путь-к-файлу>
  ```
- **Сборка нативного автономного AOT-бинарника:**
  ```bash
  dart compile exe bin/stray_dart.dart -o stray
  ```
- **Запуск тестов:**
  ```bash
  dart test
  ```
- **Обновление зависимостей:**
  ```bash
  dart pub get
  ```

---

## 6. Коды завершения (Exit Codes)

- `0`: Успех (или `--help`, `--version`).
- `1`: Ошибка пользователя / входных данных (файл отсутствует/не найден, файл пуст, неверные флаги/аргументы).
- `2`: Непредвиденная внутренняя системная ошибка.
