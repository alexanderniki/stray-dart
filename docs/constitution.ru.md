# Constitution: stray-dart

## 1. Цель и видение проекта (Vision & Scope)
`stray` — легковесная, надежная и быстрая консольная утилита на языке Dart, предназначенная для случайного выбора и вывода строки из текстового файла.

Ключевые ценности:
- **Предсказуемость:** детерминированное поведение, прозрачные коды завершения, дружелюбные сообщения об ошибках без неконтролируемых стектрейсов.
- **Минимализм:** отсутствие тяжелых сторонних фреймворков и транзитивных зависимостей.
- **Надежность:** полное соответствие принципам Spec-Driven Development (SDD), покрытие тестами каждого сценария спецификации.

---

## 2. Архитектурные принципы (Architectural Principles)

### 2.1. Pragmatic Hexagonal Architecture (Слоистая изоляция)
Кодовая база разделена на четко разграниченные слои с однонаправленным потоком зависимостей:
1. **`domain/` (Бизнес-логика):**
   - Чистый Dart, полная изоляция от `dart:io` и внешних пакетов.
   - Содержит алгоритм выборки (`StringPicker`), доменные контракты (порты/интерфейсы `LineReader`, `RandomGenerator`) и доменные сущности.
2. **`infrastructure/` (Адаптеры I/O):**
   - Реализация интерфейсов доступа к файловой системе через `dart:io` (`FileLineReader`) и системного генератора случайных чисел.
3. **`cli/` (Консольный интерфейс):**
   - Парсинг флагов и аргументов командной строки (`package:args`).
   - Валидация входных данных пользователя.
   - Маппинг доменных ошибок в текстовые сообщения и exit-коды процесса.
4. **`bin/stray_dart.dart` (Composition Root):**
   - Точка входа в приложение.
   - Исключительно сборка графа зависимостей (ручной Constructor Injection) и передача управления в CLI-раннер.

### 2.2. Модель обработки ошибок (Result Pattern)
- Никаких необработанных исключений (`throw`) для ожидаемых бизнес-сценариев и ошибок ввода-вывода. Исключения зарезервированы только для критических программных сбоев (bugs/assertions).
- Все операции, способные завершиться неудачей, возвращают легковесный тип `Result<T, AppError>` (варианты `Success` и `Failure`).
- Типизированные ошибки (`AppError`) иерархичны и содержат контекст, необходимый для вывода понятного сообщения пользователю.

### 2.3. Неизменяемость и чистота функций
- Доменные сущности и объекты конфигурации объявляются как `immutable` с `final`-полями и `const`-конструкторами, где это возможно.
- Алгоритмы доменного слоя проектируются как чистые функции, зависящие только от переданных аргументов.

## 3. Стандарты качества и читаемости кода (Code Quality)

### 3.1. Анализ и строгость типизации
- Базовый набор правил: `package:lints/recommended.yaml`.
- Строгий режим компилятора (`analysis_options.yaml`):
  ```yaml
  analyzer:
    language:
      strict-casts: true
      strict-inference: true
      strict-raw-types: true
  ```
- Нулевая толерантность к `dynamic` (за исключением внешних нетипизированных API, где требуется немедленный кастинг в строгий тип).
- Полная поддержка Sound Null Safety (запрет на оператор `!` без предварительной проверки).

### 3.2. Стиль и форматирование
- Весь код форматируется официальным `dart format` (длина строки — 80 символов).
- Отсутствие неиспользуемых импортов и переменных.
- Публичный API слоев документируется лаконичными Dartdoc-комментариями (`///`).

## 4. Spec-Driven Development (SDD) и стратегия тестирования

### 4.1. Цикл разработки фичи
Разработка любой новой функциональности или изменение контракта выполняется строго по циклу:
1. **Спецификация (`spec/<feature>.spec.md`):** описание требований, контрактов ввода-вывода, граничных случаев и сценариев.
2. **Согласование:** ревью спецификации архитектором проекта.
3. **Тесты (Red):** написание модульных и/или сквозных тестов под описанные сценарии (тесты падают).
4. **Реализация (Green):** написание минимально необходимого кода для прохождения тестов.
5. **Рефакторинг:** улучшение структуры кода при зеленых тестах и проверках `dart analyze`.

### 4.2. Формат спецификаций
Каждая спецификация в `spec/` должна содержать:
- **Context & Goals:** назначение функции.
- **CLI & I/O Contracts:** флаги, аргументы, формат вывода, exit-коды.
- **Edge Cases:** пустой файл, отсутствие прав на чтение, переносы строк CRLF/LF, спецсимволы UTF-8.
- **Acceptance Scenarios:** сценарии в стиле BDD (`Given` — начальные условия, `When` — действие, `Then` — ожидаемый результат).

### 4.3. Пирамида тестирования и детерминизм
- **Unit-тесты (Domain):** тестируют логику выбора строки на 100% изолированно с использованием `FakeLineReader` и детерминированного `Random` (с фиксированным seed).
- **Интеграционные/E2E-тесты (CLI):** запускают утилиту или CLI-команду с реальными временными файлами (`Directory.systemTemp`), проверяя соответствие вывода `stdout`, `stderr` и кодов возврата.
- Все тесты должны выполняться быстро (<2 секунд на весь набор) и быть абсолютно детерминированными (без флакующих тестов).

## 5. Политика зависимостей (Dependencies Policy)

- **Минимализм:** в `dependencies` разрешены только официальные пакеты, критически необходимые для CLI (в настоящий момент — `args: ^2.7.0`).
- **Собственные реализации базовых паттернов:** `Result<T, E>` и внедрение зависимостей реализуются на чистом Dart без привлечения сторонних тяжелых библиотек (`fpdart`, `get_it` и т.д.).
- Любое добавление новой зависимости в `pubspec.yaml` требует явного архитектурного обоснования и согласования.

## 6. Технические стандарты и ограничения CLI

### 6.1. Exit-коды (упрощенный стандарт)
- `0`: Успешное выполнение.
- `1`: Ошибка пользователя / входных данных (файл не найден, файл пуст, неверные аргументы командной строки).
- `2`: Внутренняя непредвиденная ошибка системы.

### 6.2. Потоки вывода (I/O Separation)
- `stdout`: строго для полезного вывода (выбранная строка, текст справки `--help`, номер версии `--version`).
- `stderr`: строго для диагностических сообщений и ошибок (с префиксом вида `Error: ...`).
- Поддержка Unix-пайплайнов (`stray file.txt | cat`).

### 6.3. Кроссплатформенность и кодировки
- Текстовые файлы: строго кодировка UTF-8.
- Корректная обработка окончаний строк как Unix (`\n`), так и Windows (`\r\n`).
- Корректная работа с путями на всех целевых ОС (macOS, Linux, Windows).
- Поддержка запуска через `dart run` и нативной компиляции в бинарный файл (`dart compile exe`).

### 6.4. Эволюция чтения данных
- **Фаза MVP:** Чтение файла в память (`List<String>`) через `FileLineReader`.
- **Будущая оптимизация:** Замена реализации `LineReader` на потоковую выборку (*Reservoir Sampling*) с $O(1)$ по памяти для поддержки файлов любого объема. Благодаря архитектурному порту замена не затронет логику `domain` и `cli`.

## 7. Контракт взаимодействия с AI-агентом (AI Collaboration Rules)

1. **Никакого кода без спеки:** AI не пишет и не меняет реализацию фичи, пока соответствующая спецификация в каталоге `spec/` не утверждена пользователем.
2. **Соблюдение TDD:** AI сначала создает падающие тесты, подтверждает их корректность, и лишь затем приступает к имплементации.
3. **Архитектурная дисциплина:**
   - AI не импортирует `dart:io` в слой `domain/`.
   - AI не добавляет новые зависимости в `pubspec.yaml` без согласования.
   - AI не изменяет утвержденные контракты и интерфейсы без предупреждения.
4. **Обязательные проверки качества (Quality Gates):**
   Перед передачей любого шага пользователю AI обязан убедиться, что:
   - `dart format` применен ко всем измененным файлам.
   - `dart analyze` проходит с 0 предупреждений и 0 ошибок.
   - `dart test` проходит успешно (100% тестов зеленые).
